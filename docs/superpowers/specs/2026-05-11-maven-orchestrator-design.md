# Maven Orchestrator + Sidebar Test Toggle

**Date:** 2026-05-11  
**Status:** Approved

---

## Problem

The current pipeline uses Claude Opus 4.6 to generate Help Scout draft replies. Per-ticket cost is high. MavenAGI is a cheaper AI support platform that can be pre-loaded with our knowledge base and policies. We want to run Maven in parallel with the existing Claude pipeline so we can evaluate draft quality before fully switching.

---

## Solution Overview

Add a second orchestrator (`maven_orchestrator.py`) that runs the same triage → account lookup → Stripe enrichment steps as the existing `orchestrator.py`, but replaces the Claude draft call with a MavenAGI SDK call. The Help Scout sidebar gets two buttons — one per engine — so agents can trigger either pipeline on demand and compare quality. A live log panel in the sidebar supports troubleshooting.

---

## Architecture

### New file: `maven_orchestrator.py`

Mirrors `orchestrator.py` structure. Shared steps (triage, account lookup, Stripe) are called identically. The draft step is replaced:

1. Instantiate `MavenAGI` client using env vars `MAVEN_ORG_ID`, `MAVEN_AGENT_ID`, `MAVEN_APP_ID`, `MAVEN_APP_SECRET`
2. Call `client.conversation.initialize()`:
   - `conversation_id.reference_id` = Help Scout conversation ID (e.g. `"hs-{cid}"`)
   - `subject` = ticket subject
   - `messages` = prior thread messages (for replies); empty for new tickets
3. Call `client.conversation.ask_stream()`:
   - `conversation_id` = same reference ID
   - `conversation_message_id.reference_id` = `"hs-{cid}-msg-{unix_ms}"` — use current epoch milliseconds so retries always get a fresh ID (Maven ignores duplicate message IDs silently)
   - `user_id.reference_id` = customer email (or `"unknown"`)
   - `text` = ticket body (latest customer message)
   - `transient_data` = `{"account_context": account_blob, "stripe_context": stripe_block}`
   - `timezone` = `"America/New_York"` (default)
4. Collect streaming chunks into a full reply string
5. Post to Help Scout as a draft: `POST /v2/conversations/{id}/reply` with `draft: true`
6. Post a lightweight internal note: "Draft generated by Maven AGI" + Maven conversation ID

**Classification stubs** (Maven doesn't return structured JSON):
- `needs_action = True` (safe default — always send for human review)
- `auto_sendable = False` (always false; matches existing policy)
- `escalated = False`
- `confidence = "n/a (maven)"`

**Return shape** matches `orchestrator.py`'s `out` dict so `sidebar_server.py` can handle both uniformly.

---

### Changes to `sidebar_server.py`

**Two buttons** side-by-side:
- "Generate Claude Draft" → calls `/trigger-draft` with `{"engine": "claude", ...}`
- "Generate Maven Draft" → calls `/trigger-draft` with `{"engine": "maven", ...}`

**`/trigger-draft` endpoint** gains an `engine` field (default: `"claude"`). Routes to:
- `process_ticket_sync` from `orchestrator.py` for `claude`
- `process_maven_ticket_sync` from `maven_orchestrator.py` for `maven`

**Live log panel** below the buttons:
- Server-side: `_set_status()` is extended to accumulate a `logs: [str]` list per conversation ID
- `_append_log(cid, message)` helper timestamps and appends each pipeline step
- `/trigger-status/{cid}` response gains `logs` field: array of timestamped strings
- Client-side: polling loop appends new log lines to a scrollable `<pre>` element every 3 seconds

Log points emitted by `maven_orchestrator.py`:
- `[HH:MM:SS] Triage complete`
- `[HH:MM:SS] Account lookup: {email} — {found/not found}`
- `[HH:MM:SS] Stripe: {skipped/enriched}`
- `[HH:MM:SS] Maven: initializing conversation`
- `[HH:MM:SS] Maven: asking...`
- `[HH:MM:SS] Maven: response received ({N} chars)`
- `[HH:MM:SS] Help Scout: draft created`
- `[HH:MM:SS] Done`

## New Environment Variables

```bash
MAVEN_ORG_ID          # MavenAGI organization ID
MAVEN_AGENT_ID        # MavenAGI agent ID
MAVEN_APP_ID          # MavenAGI app ID
MAVEN_APP_SECRET      # MavenAGI app secret
```

The existing `DRAFT_ENGINE` env var is **not** used — the sidebar buttons make the choice explicit per-trigger. This avoids accidentally routing production webhook traffic to Maven before quality is validated.

---

## Data Flow

```
Help Scout sidebar button ("Generate Maven Draft")
  → POST /trigger-draft  {engine: "maven", conversation_id, customer_email, secret}
    → maven_orchestrator.process_maven_ticket_sync(cid, email)
        1. run_triage()                          — same as orchestrator.py
        2. fetch_account_contexts_for_ticket()   — same
        3. fetch_stripe_context()                — same (Stripe only)
        4. maven.conversation.initialize()       — subject + thread
        5. maven.conversation.ask_stream()       — ticket body + transient_data
        6. Help Scout POST /reply (draft: true)  — same
        7. Help Scout POST /notes                — lightweight note
  → sidebar polls /trigger-status/{cid} every 3s
    → renders logs + done/error state
```

---

## What's Not in Scope

- Routing production webhook traffic through Maven (webhook_server.py is unchanged)
- Auto-send via Maven (same gate as Claude: always `auto_sendable = False`)
- Structured classification from Maven (no escalation routing, no policy references)
- Removing the Claude pipeline

---

## Success Criteria

1. Clicking "Generate Maven Draft" in the sidebar creates a Help Scout draft within 30s
2. The log panel shows step-by-step progress with no silent failures
3. Both buttons can be used independently on the same conversation without conflict
4. Maven credentials missing → clear error in log panel, not a 500
